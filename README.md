# GRAY Editor — Telegram-бот для «Предложенных новостей» ВКонтакте

Бот для редактора **Winston_Goodman** (сообщество Black Russia, сервер GRAY): планирует записи по дням недели и в нужное время отправляет их в раздел **«Предложить новость»** (предложенные записи) сообщества VK через официальный VK API. Прямых публикаций на стену бот не делает.

---

## 0. Главное ограничение VK (прочтите до настройки)

По документации VK, метод `wall.post` создаёт **предложенную** запись, только если `owner_id` — сообщество, в котором **текущий пользователь не является руководителем**. Отсюда:

1. **Токен сообщества не подходит** — `wall.post` доступен только с пользовательским токеном.
2. **Аккаунт самого редактора (руководителя) не подходит**: его записи VK публикует сразу, а не в предложку.
3. Нужен **отдельный обычный аккаунт VK** (не админ/редактор/модератор этого сообщества), от имени которого бот «предлагает» записи. Рабочий процесс: бот предлагает → редактор в VK одобряет/публикует из «Предложенных».
4. Стена сообщества должна позволять предлагать новости (режим «Ограниченная»; при «Открытой» записи обычных участников, скорее всего, публикуются сразу).

Как бот защищается от «случайной публикации вместо предложки»:
- перед отправкой проверяет через `groups.getById`, что аккаунт токена **не руководитель**, а стена не выключена/не открыта; иначе отправка **не выполняется**, а владельцу приходит понятная причина;
- после `wall.post` проверяет по `post_type`, что запись именно `suggest`; если VK всё же опубликовал её на стене — бот сообщает об этом и **блокирует дальнейшие отправки** до перезапуска;
- успехом считается только ответ VK с `post_id`. Если проверить запись не удалось — статус «⚠️ принято VK, но не подтверждено», а не «✅».

> Я не мог вызвать VK API из среды разработки (нет доступа в сеть и реальных токенов), поэтому поведение VK подтверждено только документацией и сторонними источниками, **не живым тестом**. Перед боевым использованием выполните `/vkcheck` и `/vktest` (раздел 4.6) — это единственный надёжный способ убедиться.

## 2. Что умеет бот

- **➕ Добавить пост**: текст с фото одним сообщением (фото с подписью) или просто текст → тема (необязательно) → день недели → «один раз / каждую неделю» → предпросмотр → **Подтвердить / Изменить / Отменить**.
- **📋 Активные посты**: список по 5 штук с постраничной навигацией; у каждого поста день, время, статус (⏳ ожидает, ✅ отправлено, ❌ ошибка, ❓ результат неизвестен), начало текста, 📷 если есть фото; кнопки **👁 Просмотреть / ✏️ Изменить / 🗑 Удалить**. В «Просмотре» — полный текст и фото. Для ошибок и неизвестных исходов есть «🔁 Отправить ещё раз».
- **📊 Отчёты**: журнал отправок (дата, название/начало текста, результат, причина ошибки). **Ежедневно в `REPORT_TIME` (по умолчанию 11:00)** приходит отчёт за предыдущие 24 часа (или «Отправок не было»).
- Можно создать сколько угодно постов, в том числе несколько на один день; у каждого своя тема, текст, фото.
- **Время отправки у всех постов одно — 11:00 по Москве** (`SEND_TIME`, `TIMEZONE`). Выбирать время в боте не нужно.
- Расписание хранится в БД и после перезапуска сервера работает без действий с вашей стороны. Часовой пояс по умолчанию `Europe/Moscow` (переменная `TIMEZONE`).

### Как устроена отправка и защита от дублей

- В «окне отправки» (два часа начиная с `SEND_TIME`, каждые `TICK_SECONDS` секунд), а также сразу после запуска сервиса планировщик «захватывает» созревшие посты **атомарной** операцией в БД (`pending → sending` + запись в журнал). Один пост не может быть захвачен дважды: ни параллельным запуском задачи, ни после рестарта. Дополнительно стоит уникальный индекс на «пост + время».
- Если сервер упал **во время** отправки, результат неизвестен (запись могла уйти). Бот **не повторяет** её сам: после рестарта помечает «❓» и просит проверить предложку VK.
- Обрыв сети в момент `wall.post` тоже даёт «❓», а не повтор. Ошибки до создания записи (лимит запросов, сеть при загрузке фото) безопасно повторяются.
- Если сервер был выключен и время отправки прошло больше чем на `MISSED_GRACE_MINUTES` (по умолчанию 120), пост **не отправляется задним числом**: статус «пропущено», уведомление вам; еженедельный пост переходит на следующую неделю.
- Резервные копии БД — каждую ночь в 03:30 в `data/backups` (хранятся 7 последних). Фото сохраняются на диск в `data/media`.

## 4. Подключение VK API

### 4.1 Подготовьте аккаунт-отправитель
Используйте отдельный обычный аккаунт VK (своего второго или специально созданного — с соблюдением правил VK). Он **не должен** быть руководителем этого сообщества. Желательно, чтобы он был подписан на сообщество.

### 4.2 Настройте сообщество
Управление → Разделы → **Стена: «Ограниченная»** (участники могут предлагать новости). ID сообщества (число) впишите в `VK_GROUP_ID`.

### 4.3 Создайте Standalone-приложение
vk.com/editapp?act=create → тип **Standalone-приложение** (под аккаунтом-отправителем). Запомните **ID приложения**.

### 4.4 Получите токен
```bash
python scripts/vk_token_helper.py <ID_приложения>
```
Откройте ссылку под аккаунтом-отправителем, подтвердите права (`wall`, `photos`, `offline`), вставьте адрес, на который вас перенаправит VK. Скрипт выведет `VK_USER_TOKEN=...` — сохраните в `.env`.

Что важно знать:
- VK постепенно переводит авторизацию на VK ID; порядок выдачи токенов и срок их жизни могут меняться. Если токен истечёт, VK вернёт ошибку 5 — бот сообщит об этом при очередной отправке, и токен нужно получить заново (шаг 4.4).
- **Не используйте неофициальные токены** (от «Kate Mobile», «VK Admin» и т. п.): это нарушает правила VK и может привести к блокировке аккаунта.
- Токен — это пароль к аккаунту. Храните только в `.env` (права `600`), не публикуйте.

### 4.5 (Необязательно) Токен для проверки принятия
`VK_ADMIN_TOKEN` — токен руководителя сообщества с правом `wall`. Используется **только для чтения** (`wall.get` с `filter=suggests`, `wall.getById`), чтобы надёжно подтверждать, что запись оказалась в предложенных. Без него бот пытается проверить токеном аккаунта-отправителя; если VK не разрешает — статус «⚠️ принято, но не подтверждено».

### 4.6 Проверка перед боевым запуском
В боте:
- `/vkcheck` — ничего не публикует: показывает сообщество, роль аккаунта, режим стены и проблемы конфигурации.
- `/vktest` — создаёт **настоящую** тестовую запись в «Предложенных» (потом удалите её в VK). Ожидаемый ответ: «✅ … VK подтвердил: post_type = suggest».
Если бот пишет, что запись опубликована на стене или что аккаунт — руководитель, исправьте роль аккаунта/режим стены, не продолжайте.

## 5. Развёртывание на Render (бесплатный тариф)

Проект подготовлен под **Free Web Service** Render. Что важно знать о бесплатном тарифе (по [документации Render](https://render.com/docs/free)):

- сервис **засыпает через 15 минут без входящих HTTP-запросов** (пробуждение — около минуты);
- файловая система **не сохраняется** при рестарте, деплое и засыпании — поэтому SQLite-файл и фото на диске терять нельзя;
- встроенный бесплатный Postgres Render **удаляется через 30 дней**, поэтому используется внешняя бесплатная база;
- фоновые воркеры бесплатно недоступны — бот работает как Web Service и отвечает на `GET /health`;
- на бесплатный тариф даётся 750 часов в месяц на аккаунт — одного круглосуточного сервиса хватает.

Как это решено в проекте: данные и **фото хранятся в Postgres** (`DATABASE_URL`), сервис отвечает на `/health` и сам обращается к себе каждые 4 минуты, посты уходят **в 11:00 МСК**.

### 5.1 Бесплатная база Postgres (Neon)

1. Зарегистрируйтесь на [neon.com](https://neon.com), создайте проект (регион — Frankfurt).
2. Скопируйте **connection string** (`postgresql://…?sslmode=require`) — это `DATABASE_URL`.
3. Таблицы бот создаёт сам при первом запуске. Бесплатный Neon засыпает через 5 минут без запросов; бот обращается к базе только при действиях в Telegram и в «окне отправки» около 11:00, поэтому лимит бесплатных часов не расходуется впустую.

### 5.2 Деплой

1. Выложите проект в **приватный** репозиторий GitHub (`.env` и `data/` в Git не попадают — см. `.gitignore`).
2. В Render: **New → Blueprint** → выберите репозиторий (подхватится `render.yaml`), либо **New → Web Service → Docker** с планом **Free**.
3. Введите секреты: `BOT_TOKEN`, `OWNER_ID`, `VK_USER_TOKEN`, `VK_GROUP_ID`, `VK_ADMIN_TOKEN` (по желанию), `DATABASE_URL`.
4. После деплоя откройте `https://<имя>.onrender.com/health` — должно быть `ok`. В Telegram отправьте боту `/vkcheck`.

### 5.3 Чтобы сервис не засыпал (обязательно)

Самопроверка бота работает, только пока сервис проснулся. Если он всё же уснёт (рестарт, деплой, сбой), разбудить его может только внешний запрос. Поэтому настройте бесплатный внешний пинг адреса `https://<имя>.onrender.com/health` **каждые 5 минут** — например, в [UptimeRobot](https://uptimerobot.com) или [cron-job.org](https://cron-job.org).

Если сервис проснулся позже 11:00, но не позже чем через `MISSED_GRACE_MINUTES` (120 мин), пост уйдёт сразу при пробуждении. Если позже — пост помечается «пропущено» и вы получаете уведомление, задним числом он не отправляется.

### 5.4 Что стоит помнить

- Render может перезапустить бесплатный сервис в любой момент. Если это случилось ровно во время отправки, результат помечается «❓» — проверьте «Предложенные» в VK.
- На время деплоя могут одновременно работать старый и новый экземпляр: дублей постов нет (захват поста атомарен в БД), возможны лишь краткие сообщения Telegram о конфликте опроса.
- Резервные копии Postgres обеспечивает провайдер (в бесплатном Neon окно восстановления короткое, около 6 часов); локальные копии `backups/` делаются только для SQLite.
- Лимиты и условия бесплатных тарифов меняются — перед запуском сверьтесь с актуальными страницами Render и Neon.

## 5a. Развёртывание на своём облачном сервере (Ubuntu 22.04/24.04, Docker)

```bash
# 1. Docker
curl -fsSL https://get.docker.com | sudo sh
sudo usermod -aG docker $USER && newgrp docker

# 2. Код проекта на сервер (git clone или scp -r gray_editor user@IP:~/)
cd ~/gray_editor

# 3. Настройки
cp .env.example .env
nano .env                  # заполните BOT_TOKEN, OWNER_ID, VK_USER_TOKEN, VK_GROUP_ID
chmod 600 .env

# 4. Каталог данных (контейнер работает от пользователя uid 10001)
mkdir -p data && sudo chown -R 10001:10001 data

# 5. Запуск
docker compose up -d --build
docker compose logs -f     # Ctrl+C — выйти из просмотра, бот продолжит работать
```

Полезно:
- `docker compose restart` — перезапуск; `docker compose down` — остановка.
- Обновление кода: заменить файлы → `docker compose up -d --build`. Данные в `./data` сохраняются.
- `restart: unless-stopped` поднимает бота после перезагрузки сервера.
- Восстановление из копии: остановить бота, заменить `data/gray_editor.sqlite3` файлом из `data/backups/`, запустить.
- Любой VPS подходит (1 vCPU / 512 МБ достаточно). Исходящий доступ нужен к `api.telegram.org`, `api.vk.com` и серверам загрузки фото VK.

2. `/vkcheck` → «✅ Проверка VK», затем `/vktest` → «✅ … suggest»; удалите тест в VK.

## 8. Безопасность

- Доступ — только `OWNER_ID`; сообщения других пользователей игнорируются.
- Секреты — только в переменных окружения; в логах и сообщениях об ошибках токены заменяются на `***`; токен VK передаётся в теле POST-запроса, а не в URL.
- Контейнер работает от непривилегированного пользователя; `.env` и `data/` исключены из Git и Docker-образа.

## 9. Ограничения и допущения

- Подтверждение «предложенная запись» опирается на `post_type = suggest`, который VK возвращает при чтении записи; без `VK_ADMIN_TOKEN` чтение чужой предложки может быть недоступно — тогда статус будет «не подтверждено».
- Текст в VK уходит без форматирования (VK не поддерживает разметку Telegram). Альбомы из нескольких фото не поддерживаются: один пост — одно фото.
- Хранилище — SQLite (для одного редактора этого достаточно). Состояние диалога создания поста хранится в памяти: при перезапуске незавершённый черновик нужно начать заново; сохранённые посты не теряются.
- Лимиты VK (число записей в сутки, антиспам, капча) действуют на аккаунт-отправитель; при отказе бот сохранит причину и сообщит вам.
